# GearLead AI 面试辅导手册

## 一、这份手册训练什么

你的目标不是证明自己是全栈工程师，而是证明你具备AI解决方案实习生需要的能力：

1. 调研并描述客户业务问题。
2. 把模糊痛点拆成结构化需求。
3. 判断哪些任务适合LLM、规则、数据库和人工。
4. 使用Python和FastAPI完成可调用的POC。
5. 设计测试、说明边界并输出解决方案材料。
6. 面向客户或面试官清楚表达方案价值。

前端界面由AI辅助编程完成没有问题。你需要掌握的是页面展示了什么业务结果，不需要讲前端框架和实现细节。

## 二、项目主线

请记住一句话：

> 外贸询盘是非结构化英文，但SKU、MOQ、产品参数、风险和商业承诺必须结构化、可解释、可审核。因此我设计了一个混合式AI工作流：LLM或规则解析语言，Pydantic校验结构，SQLite提供产品事实，简单规则处理关键业务决策，FastAPI提供接口，业务员完成最终审核。

## 三、30秒项目介绍

> 我完成了GearLead AI，一个面向电竞外设出口企业的英文询盘资格评估与产品匹配Agent。系统覆盖鼠标、机械键盘、耳机、客制化线材和键帽五类产品，可以提取客户与采购需求，查询20个SKU，识别标准产品、轻度定制、ODM或无匹配，计算线索优先级，并生成英文跟进草稿。我采用LLM与规则结合的方案：模型负责语言理解和表达，数据库和规则负责产品事实、硬约束和风险路由，最后由业务员审核。项目同时通过FastAPI提供五个基础接口，并用25条合成询盘完成POC回归测试。

## 四、两分钟完整介绍

> 我先把项目范围限定在“收到英文询盘到形成首轮跟进决策”，没有扩展到自动报价、发信、合同和物流。通过模拟需求调研，我把痛点归纳为询盘信息分散、新人不熟悉SKU、关键参数容易遗漏、低质量和风险询盘混淆、回复标准不统一。
>
> 然后我把业务流程拆成七步：询盘提取、完整性检查、客户和风险检查、产品匹配、线索评分、策略路由、回复生成。提取结果使用Pydantic校验；产品事实来自SQLite；关键参数采用硬约束，例如键盘布局、热插拔和语言布局，冲突时不能判定为标准SKU；质量提醒、商业提醒和风险信号分开处理，只有真实风险强制人工复核。
>
> 技术入口有两个：Streamlit用于演示，FastAPI提供分析、产品和CRM接口，两者复用同一个工作流。为了验证POC，我使用25条合成询盘做回归测试，并补充跨国市场、硬约束冲突、异常付款和否定表达等反例。所有回复都是草稿，系统不自动承诺价格、交期和认证。

## 六、需求调研怎么讲

推荐按四步回答：

1. 明确用户：外贸业务员，销售主管是辅助用户。
2. 限定流程：只解决首轮询盘处理，不覆盖成交后的合同和履约。
3. 找出痛点：信息提取、产品查询、资格判断、回复和记录。
4. 定义验收：关键字段可提取、硬约束不误判、风险可升级、回复可审核。

不要说“客户需要一个AI Agent”。客户真正需要的是缩短询盘处理时间、减少产品误判并统一跟进流程。Agent只是实现方式。

### 模拟访谈问题示例

- 一封询盘从收到到回复需要哪些步骤？
- 哪些产品参数必须由工程师确认？
- 什么情况可以直接推荐标准SKU？
- 什么情况需要ODM评估？
- 哪些异常必须停止报价并转人工？
- 业务员认为POC成功的标准是什么？

## 七、为什么不用纯LLM

> 纯LLM适合理解开放式英文，但不适合独立决定SKU、MOQ、风险和商业承诺。它可能编造产品参数，也难以保证每次评分一致。因此我把语言理解交给模型，把产品事实交给数据库，把硬约束、评分和风险路由交给规则，再用人工审核控制最终商业输出。

这体现的是技术可行性与业务风险之间的平衡。

## 八、模型在项目中的作用

### 模型负责

- 理解不同写法的英文询盘。
- 输出结构化客户、采购、产品和定制信息。
- 根据已经确定的策略生成英文回复草稿。

### 模型不负责

- 编造SKU、库存和认证。
- 决定最终报价和交期。
- 独立判断真实企业信用。
- 自动发送邮件。

### Prompt设计要点

询盘提取Prompt要求：

1. 只能输出JSON。
2. 不得补全原文没有的信息。
3. 客户国家、目标市场和交付地点必须分开。
4. 保留`not hot-swappable`等否定要求。
5. 区分质量提醒、商业提醒和风险信号。

回复Prompt要求：

1. 只能使用结构化分析和产品匹配结果。
2. 不承诺最终价格、交期、认证和技术可行性。
3. ODM请求必须说明需要工程评估。
4. 最后保留`Draft for salesperson review.`。

## 九、Pydantic怎么讲

> Pydantic是模型输出和业务规则之间的数据合同。大模型输出JSON后，系统先校验品类、数量范围和字段结构，再进入匹配和评分。这样后续模块不需要直接处理自由文本，也能在非法输出时回退到规则解析。

你需要知道：

- `BaseModel`定义数据结构。
- `Field`可以限制最小长度、数值范围和默认值。
- FastAPI会复用Pydantic完成请求校验。
- 请求不符合Schema时，FastAPI自动返回422。

## 十、产品匹配怎么讲

匹配流程只有四步：

1. 根据品类查询对应产品。
2. 对客户明确提出的规格逐项比较。
3. 先排除存在硬约束冲突的候选，再按匹配分排序。
4. 根据定制需求输出标准SKU、轻度定制、ODM或无匹配。

### 硬约束与软约束

> 硬约束是客户明确提出且不能被其他优势抵消的参数。例如客户要求全尺寸热插拔键盘，目录中的全尺寸键盘不支持热插拔，即使MOQ、布局和市场都匹配，也不能判定为标准SKU。软约束如颜色和包装可以作为轻度定制处理。

这是项目中最重要的业务规则。

## 十一、风险分类怎么讲

系统不再把所有异常都称为风险：

- 质量提醒：内容太短、只问最低价、信息不完整。
- 商业提醒：独家要求缺少渠道信息、目标市场为推断值、大额订单资料不足。
- 风险信号：异常付款、索要敏感材料、绕过合同、CRM高风险状态。

只有风险信号会覆盖分数，进入`Risk Review`。低质量询盘得分低，但仍然可以正常培育，不应该被当成欺诈客户。

## 十二、评分怎么讲

评分用于排序，不用于自动拒绝客户。

| 维度 | 分值 |
|---|---:|
| 客户可信度 | 20 |
| 需求明确度 | 20 |
| MOQ匹配 | 15 |
| 产品或定制可行性 | 20 |
| 商业价值 | 15 |
| 紧迫度 | 10 |

面试时不要逐条背代码。说明为什么这些维度能支持业务员决定“先跟进谁”即可。

## 十三、FastAPI必须掌握的内容

### 1. FastAPI是什么

> FastAPI是Python Web API框架。我使用它把GearLead的分析、产品查询和CRM保存能力暴露为REST接口，使页面、Postman或其他系统都可以调用同一套业务逻辑。

### 2. 五个接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 检查服务状态 |
| POST | `/api/v1/inquiries/analyze` | 分析英文询盘 |
| GET | `/api/v1/products` | 查询产品目录 |
| POST | `/api/v1/leads` | 保存审核后的线索 |
| GET | `/api/v1/leads` | 查询线索记录 |

### 3. GET和POST区别

- GET用于读取数据，例如查询产品和线索。
- POST用于提交数据并产生分析或新增记录。

### 4. 请求和响应

分析请求：

```json
{
  "inquiry_text": "We need 500 gaming mice...",
  "use_llm": false
}
```

FastAPI先用`AnalyzeInquiryRequest`校验请求，再调用`analyze_inquiry`，最后把`WorkflowResult`序列化成JSON响应。

### 5. 常见状态码

- `200 OK`：查询或分析成功。
- `201 Created`：CRM线索保存成功。
- `400 Bad Request`：业务输入无法处理。
- `422 Unprocessable Entity`：请求没有通过Pydantic校验。
- `500 Internal Server Error`：服务内部异常。

### 6. Swagger

启动API后访问：

```text
http://127.0.0.1:8000/docs
```

Swagger会展示接口路径、请求Schema、响应Schema和在线调试按钮。

### 7. 启动和调试

```bash
uvicorn api:app --reload
```

```bash
curl http://127.0.0.1:8000/health
```

你不需要解释复杂前后端，只要能画清楚：

```text
调用方 → FastAPI → GearLead工作流 → SQLite/LLM → JSON响应
```

## 十四、为什么称为Agent

> 它不是开放式自主Agent，而是受限的workflow-based Agent。系统围绕“完成首轮询盘处理”这一业务目标，依次调用提取、检查、匹配、评分、路由和回复工具。每一步输入输出明确，关键决策可解释，最后由人工批准。

如果被问到OpenClaw：

> 当前POC使用原生Python编排，便于控制难度和验证核心流程。如果企业采用OpenClaw，可以将FastAPI分析、产品查询和CRM接口封装为OpenClaw可调用工具，业务规则和数据服务无需重写。当前项目没有宣称已经完成真实OpenClaw集成。

## 十五、POC怎么讲

> POC不是为了证明系统已经可以生产上线，而是验证方案链路是否成立。我使用25条合成询盘覆盖五类产品、完整、缺失、ODM、低质量和风险场景，并补充跨国市场、硬约束冲突、异常付款和否定表达反例。测试可以重复运行，但数据参与过规则调优，因此结果属于回归指标，不代表真实询盘泛化性能。

必须准确说明：

- 基础字段准确率只统计品类、数量和客户国家。
- 产品匹配准确率来自小型合成集。
- 回复完整率只代表格式满足要求。
- 下一步应使用匿名真实询盘和业务员标注。

## 十六、售前材料怎么讲

项目输出三类方案材料：

1. 需求调研：客户背景、现状流程、痛点、访谈问题和需求优先级。
2. 解决方案：目标流程、架构、组件职责、业务规则、范围和价值假设。
3. POC报告：验收标准、测试结果、反例、限制和下一阶段建议。

这说明你不仅能写Demo，也能支持客户沟通和售前方案表达。

## 十八、常见面试问题

### 为什么选择这个场景？

电竞外设询盘既有非结构化英文，又有结构化产品参数和OEM/ODM判断，能够同时验证大模型理解、数据库查询、业务规则和人工审核。

### 为什么不直接用ChatGPT生成邮件？

项目价值不只是写邮件，而是先完成需求提取、产品匹配、资格判断和跟进决策。邮件只是最后一个输出。

### 为什么产品库不用RAG？

SKU、MOQ、布局和接口等数据需要精确比较，结构化数据库更适合。RAG可以在以后用于产品手册、FAQ和认证文件，但不应替代产品主数据。

### 模型返回非法JSON怎么办？

Pydantic校验失败后回退到规则解析器，避免错误数据进入匹配和评分。

### 为什么仍然保留规则？

规则只保留关键、可解释的业务边界，例如硬约束和风险路由。它不是为了覆盖所有语言，而是防止模型在关键决策上越界。

### 前端是不是你写的？

> Streamlit页面由AI辅助编程完成。我负责定义业务流程、页面需要展示的结果和验收标准，并完成整体测试。这个项目中我重点掌握的是模型应用、业务逻辑、数据结构和FastAPI接口。

### 项目最大的限制是什么？

合成询盘不能代表真实客户语言；产品库没有实时库存、价格和认证版本；LLM路径依赖外部服务；系统只覆盖首轮跟进，不包含完整外贸履约流程。

### 如何衡量真实业务价值？

试点阶段应记录首轮回复准备时间、字段纠错率、产品推荐接受率、回复采用率、人工升级率和业务员满意度。

## 十九、STAR表达

**Situation：** 电竞外设外贸询盘参数多、质量不一，新业务员查询产品和准备回复依赖经验。

**Task：** 设计一个中等难度POC，验证AI能否辅助首轮询盘理解、产品匹配和跟进决策，同时控制商业风险。

**Action：** 我模拟需求调研，限定业务边界，设计结构化Schema、LLM提示词、20个SKU数据库、硬约束匹配、风险分层、线索评分、FastAPI接口和人工审核流程，并编写合成测试集与POC报告。

**Result：** 完成可运行的Streamlit Demo和五个REST API，形成从询盘输入到CRM保存的完整链路，关键业务反例和24项自动化测试通过。测试结果用于课程项目回归，不宣称生产准确率。
