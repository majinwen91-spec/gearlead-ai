# GearLead AI 面试培训手册

这份手册的目标不是让你背代码，而是让你能从业务问题、方案设计、技术实现、测试结果和风险边界五个层次完整复述项目。

## 一、先掌握项目主线

请记住这条主线：

> 外贸英文询盘是非结构化输入，但产品、MOQ、评分和商业承诺必须结构化、可解释、可审核。因此我设计了一个混合式 Agent：LLM 或规则解析器负责理解语言，Pydantic 固定数据契约，SQLite 和规则引擎负责产品匹配与评分，业务员负责最终审核和保存 CRM。

## 二、30 秒版本

> 我做了 GearLead AI，一个面向电竞外设出口企业的英文询盘资格评估与产品匹配 Agent。它覆盖鼠标、机械键盘、耳机、客制化线和键帽五类产品，能从英文询盘中提取结构化采购需求，查询 20 个 SKU 的产品库，判断标准产品、轻度定制、ODM 或无匹配，并按六个业务维度进行 100 分评分，最后生成跟进策略和英文邮件草稿。方案采用 LLM 可选、规则兜底和人工审核，25 条合成 POC 测试集上的指标达到 PRD 门槛。

## 三、2 分钟版本

> 项目源于一个真实的外贸流程：业务员收到英文询盘后，要识别客户、提取参数、查产品、判断 MOQ 和定制可行性、决定优先级，再写首轮回复。问题在于输入很灵活，但产品事实和商业承诺不能靠模型自由发挥。
>
> 我把流程拆成七个工具：询盘提取、完整性检查、客户与风险检查、产品匹配、线索评分、策略路由和回复生成。提取结果先经过 Pydantic 校验，再进入规则层。产品库用 SQLite，因为电竞外设参数是结构化字段，用 SQL 比 RAG 更准确。匹配引擎先按品类筛选，再比较核心参数、MOQ、认证、市场和定制能力，输出 Top 3 候选及理由和缺口。
>
> 评分严格按 PRD 的六个维度，总分 100；明确风险会覆盖分数，进入人工复核。所有回复都带 Draft for salesperson review，系统不自动发信、不承诺价格和交期。为了验证 POC，我构造了 25 条人工标注的合成询盘，覆盖五类产品、完整询盘、缺失询盘、ODM、低质量和风险场景，并用 pytest 和 Evaluation 页面做回归。

## 四、5 分钟演示讲解顺序

1. 在 Inquiry Analyzer 选择 K01 德国键盘询盘。
2. 说明输入包含 75%、三模、Gasket、热插拔、PBT、ISO-DE、CE、500 台和定制包装。
3. 点击分析，展示结构化 JSON，强调 Schema 不是自由文本。
4. 打开 Lead Qualification，逐项解释六维评分和 High 路由。
5. 打开 Product Matching，说明为什么 KB75-GASKET-TM 是第一候选，以及其他 SKU 的差距。
6. 打开 Follow-up Assistant，说明系统先决定策略，再生成邮件；邮件不承诺最终价格或交期。
7. 保存 CRM，展示业务闭环和人工审核点。
8. 打开 Evaluation，主动说明数据是 25 条合成 POC 集，不代表生产泛化。

## 五、你必须能画出的架构

```text
Streamlit
   ↓
Workflow Orchestrator
   ├─ Inquiry Parser ── optional LLM
   ├─ Completeness Checker
   ├─ Customer/Risk Checker ── SQLite customers
   ├─ Product Matcher ── SQLite catalog
   ├─ Lead Scorer ── deterministic rules
   ├─ Strategy Selector
   └─ Reply Generator ── optional LLM
   ↓
Human Review
   ↓
SQLite CRM
```

讲图时不要只念组件。要说清数据怎样流动，以及为什么每个组件放在那里。

## 六、为什么这是 Agent，不是聊天机器人

推荐回答：

> 聊天机器人主要围绕自然语言对话，而我的系统围绕一个有状态的业务目标执行多个受限工具。每一步有明确输入输出，前一步的结构化结果会决定后一步的产品查询、评分和路由，最后还会产生 CRM 动作。它的 Agent 性体现在工作流编排、工具调用和条件路由，不在于让模型无限自主。

## 七、为什么不用纯 LLM

> 纯 LLM 容易在 MOQ、认证、SKU 和分数上产生幻觉，也很难稳定复现。我的设计让 LLM 只处理它擅长的语言理解和表达，产品事实来自数据库，评分和匹配来自规则，输出再经 Schema 校验和人工审核。这样既利用模型能力，也把业务风险控制在可解释范围内。

## 八、为什么产品库不用 RAG

> 核心产品数据是功率、布局、传感器、MOQ、认证等结构化字段，需要精确比较和范围判断，SQL 更合适。RAG 更适合产品手册、认证报告和 FAQ 等非结构化资料。生产版可以增加带引用的 RAG，但不应该替代结构化产品主数据。

## 九、产品匹配怎么讲

按四步回答：

1. 品类过滤，避免跨品类推荐。
2. 核心参数加权，例如键盘布局、鼠标传感器、耳机单元、线材接头、键帽材质。
3. 加入 MOQ、认证、目标市场和定制能力。
4. 根据需求和缺口路由为标准 SKU、轻定制、ODM 或无匹配，并保留 Top 3 解释。

## 十、评分怎么讲

> 总分 100，客户可信度和需求明确度各 20，MOQ 15，可行性 20，商业价值 15，紧迫度 10。High 是 80 分以上，Medium 是 60 到 79，其他是 Low。但风险不是普通扣分项：异常付款、绕过合同、敏感信息等证据会直接把结果路由到 Risk Review，避免高订单量把风险掩盖掉。

## 十一、测试怎么讲

> 我先按品类和业务难度做分层测试集，再为每条询盘标注品类、数量、国家、推荐 SKU、匹配类型、优先级和缺失字段。Evaluation Service 逐条调用完整工作流，不绕过任何工具。pytest 还覆盖 Schema、评分上限、风险覆盖、五品类匹配、CRM 持久化和回复安全提示。

必须主动补一句：

> 这是合成数据上的 POC 回归结果，样本规模小，而且规则参与了调优，所以不能宣称生产准确率。下一步要用匿名真实询盘做盲测，并由资深业务员标注。

## 十二、遇到的实际问题

你可以讲两个真实调试案例：

1. 键盘询盘里出现 “PBT keycaps” 时，早期规则把整封询盘误判成键帽。修复方法是调整品类识别优先级：只要主体明确是 keyboard，就不能被附件词 keycaps 覆盖。
2. “75% keyboard” 中的 75 一度被误识别为采购数量。修复方法是让数量规则必须结合 units、sets、pcs 等单位，并排除百分号上下文。

这两个例子能证明你不仅搭了页面，还真正处理了领域文本歧义。

## 十三、常见面试问题与答案

### 1. 为什么选电竞外设外贸？

产品参数结构化、OEM/ODM 场景明显、英文询盘真实存在，而且业务流程既包含语言理解，又包含数据库、规则和人工决策，适合展示 AI Solution 的完整闭环。

### 2. 为什么只做五类产品？

为了控制 POC 边界。五类已经能证明多 Schema、多规则和多路由能力；继续扩品类只会扩大种子数据工作量，不会验证新的核心假设。

### 3. 为什么不用 LangGraph？

第一版流程是固定 DAG，原生 Python 编排更轻、更容易调试和展示。达到多轮状态恢复、人工审批节点、并行工具和长流程要求后，再引入 LangGraph才有明确收益。

### 4. Demo mode 有什么价值？

它让面试演示不依赖网络和 API Key，同时能把规则层独立测清。LLM 只是增强路径，不是系统能否运行的单点依赖。

### 5. 如何防止模型幻觉？

限制模型职责、Pydantic 校验、数据库 grounding、固定评分规则、回复禁用承诺、失败回退和人工审核。

### 6. 客户可信度是不是征信？

不是。这里只检查企业邮箱、公司名、网站、客户类型、目标市场和模拟 CRM 状态，用于排序和人工复核，不形成信用或合规结论。

### 7. 为什么风险要覆盖分数？

因为大订单可能带来高商业价值分，但不能抵消异常付款或绕过合同等风险。覆盖式路由比简单扣分更符合控制逻辑。

### 8. 产品 Match Score 和 Lead Score 有什么区别？

Match Score 衡量某个 SKU 对技术和商业条件的适配度；Lead Score 衡量整条线索的跟进优先级。高产品匹配不等于高质量客户。

### 9. 如果 LLM 返回非法 JSON 怎么办？

捕获解析或校验异常，回退到规则解析器；无论哪条路径，进入业务规则前都必须得到合法的 `InquiryData`。

### 10. 如何上线？

先做匿名真实数据盲测，再增加身份认证、PII 加密、规则和 Prompt 版本、审计日志、监控、人工审批、CRM 沙箱连接以及回滚机制。

### 11. 如何衡量业务价值？

生产试点应测首响准备时间、业务员采纳率、字段纠错率、产品推荐接受率、风险升级命中率和人工覆盖率，而不只看离线准确率。

### 12. 项目最大的限制是什么？

合成数据不能覆盖真实询盘的语言噪声、附件、多个产品和隐含上下文；模拟产品库也没有真实库存、价格版本和认证文件。

## 十四、STAR 项目描述

**Situation：** 电竞外设外贸询盘参数复杂、质量不一，新业务员查产品和写回复耗时且标准不统一。

**Task：** 在中等难度范围内做一个可演示 POC，证明 AI 能辅助完成首轮询盘资格评估和产品匹配，同时不越过商业决策边界。

**Action：** 我拆解工作流，设计 Pydantic Schema、20 个 SKU 的 SQLite 产品库、加权匹配、六维评分、风险覆盖、四类策略和人工审核 CRM；构造 25 条 gold cases 并写自动化测试。

**Result：** 完成七页 Streamlit Demo，规则模式无需 API Key 可运行；合成 POC 集达到 PRD 阈值，并能逐条解释产品推荐、评分和风险路由。

## 十五、面试前训练任务

1. 不看文档讲完 30 秒版本，录音三次。
2. 手画一次架构图，并解释每条箭头的数据。
3. 用 K01 完成 5 分钟 Demo，不读稿。
4. 用 H04 解释为什么高数量仍然 Risk Review。
5. 用 K05 解释标准 SKU 与 ODM 的区别。
6. 主动说出两个项目限制和三个生产化改进。
7. 回答“为什么不用纯 LLM、RAG、LangGraph”三个问题。

当你能在 5 分钟内讲清业务问题、技术边界、规则证据和测试限制，这个项目才真正成为你的面试项目，而不只是一个代码仓库。
